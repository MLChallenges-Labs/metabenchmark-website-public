Why MetaBenchmark

Today's platforms aren't built for high-stakes AI

Competitions and benchmarks platforms brought people together around AI challenges. High-stakes settings need more: statistical rigor, data privacy, and evidence that the winner works in production. MetaBenchmark is built from scratch around these three needs.

The problem MetaBenchmark's answer
  1. 01

    Methodological fragility

    Leaderboards rank raw scores without confidence intervals or baselines: marginal gains look like progress, and repeated submissions overfit the test set.

    Rigorous methodology

    Benchmarking as a statistical experiment: principled ranking functions, hidden test sets, baseline comparisons and bootstrap confidence intervals.

  2. 02

    Sensitive data can't be shared

    Platforms require data on a central server, which shuts out healthcare, finance and defense.

    Data stays with its owner

    Containerized submissions run on the organizer's own servers: the raw data never leaves their infrastructure.

  3. 03

    Narrow evaluation metrics

    Accuracy, F1 or RMSE alone ignore compute cost, latency and energy, so the winner may not be fit for production.

    Production-aware evaluation

    Every submission is profiled for inference latency, peak memory and estimated carbon footprint, alongside its accuracy.

Prototype

A leaderboard is a statistical experiment

This illustrative leaderboard prototypes the ideas behind MetaBenchmark's results pages. Choose the criteria that matter to you: the ranking reorders itself, and its uncertainty changes too.

  • Error bars and ties. Every score carries a 95% bootstrap interval; methods that can't be told apart from #1 share its highlight.
  • Ranks that respect ties. On each criterion, a method's rank is 1 + the number of methods significantly better than it, so tied methods share a rank. When score and rank disagree, the choice of aggregation is what decides.
  • A baseline for reference. The dashed line marks a plain logistic regression.
  • Costs count. Latency and energy are measured on the same hardware for every submission. Add Energy and watch the fine-tuned LLM drop.

Architecture

An architecture built around your control

Technology Stack & Components

Built on React for the frontend, FastAPI for the backend, S3-compatible storage, and VMs for compute — each layer can be swapped out or self-hosted independently.

Frontend · React

A portal for admins, organizers, and participants — profile, team, competition, and submission management in one interface.

Backend · FastAPI

Handles core logic, API coordination, the database, user permissions, the submission queue, and compute connections.

Data Storage · S3

Only public metadata and sanitized scores live on the host hub; datasets, ground truth, and submission code stay on the client's local storage or S3-compatible buckets.

Compute · VMs

Evaluation tasks run in isolated containers on virtual machines; external compute resources can be attached for heavier workloads.

Prominent Features

Security and reproducibility, by design

  • Git-Integrated Workflows

    Manage training and evaluation logic through GitHub or GitLab-integrated workflows.

  • Containerized Execution

    Every submission runs in an isolated container, for fairness, reproducibility, and long-term sustainability.

  • Automated Re-Evaluation

    Results are automatically re-evaluated when organizers update a task; outdated results are flagged if re-evaluation is disabled.

  • Pre-Execution Checks

    File type and size limits, expected entry points, per-participant quotas, and rate limits are enforced before a submission ever runs.

  • Submission Scanning

    Optional scanning via predefined templates, custom scanner code, or a locally-running LLM — combinable with human-in-the-loop review before execution.

  • Network Isolation

    Execution is network-isolated by default, for security and for clean, uninfluenced resource measurements. Access can be explicitly enabled and is flagged when required (e.g. API-based LLM evaluation).

  • Decentralized Storage

    Files are routed directly to the client's linked storage (AWS S3, GCS, Azure Blob, or local hardware) — never stored centrally on MetaBenchmark's infrastructure.
